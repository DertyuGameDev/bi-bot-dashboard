# Исследование данных

Когда применять: Новая выборка, поля или источник.

Входные данные: Реальная information_schema и ограничения источника.

Последовательность: По необходимости прочитай inspect_schema: ключи, даты, numeric-поля, единицы и детализацию. sales — сделка; plan — месяц/точка/продукт; discounts — событие скидки. Для месячного плана-факта используй fetch_data. Для других вопросов используй fetch_records → analyze_records и при необходимости join_records. Новые зарегистрированные клиенты — clients.registered_date; новые контракты — contracts.start_date. Новый клиент по первой покупке — min(sales.sale_date) по client_id за ВСЮ историю, затем фильтр нужного периода. Не путай эти определения. Календарное среднее включает нулевые дни; calendar_days даёт число дней периода. Данные именованных наборов остаются между шагами; не отказывай только потому, что полей нет в месячной таблице. Для скидок возможен fetch_data(kind=discounts), но это только сделки со скидками. План на клиентов не распределён.

Инструменты: inspect_schema, fetch_data, profile_table, fetch_records, analyze_records, join_records.

Ожидаемый результат: Плоская таблица с id, версией и происхождением.

Ограничения: Не придумывай поля, серверы или единицы. Не формируй SQL. Нет ежедневного плана.

Пример: «Скидки клиента» → fetch_data(kind=discounts).

Критерии проверки: Выбранные поля существуют; пользователю показаны диапазон и источник.

Для обычной выручки/плана по точкам, регионам и времени используй fetch_data — его результат пригоден для графиков и общих фильтров. За всю историю fetch_data(all_time=true) определит границы исходных дат в pandas и выберет весь диапазон. Не оставляй прежний пустой год, не ограничивай всю историю последним полным годом. fetch_records используй для иной детализации, которой нет в месячной общей таблице.
